# Test report: mask, late tasks and close timing (QA-01)

This document records how the section 7 test suite in [WORK-BREAKDOWN.md](WORK-BREAKDOWN.md) is measured and its results, focused on the three questions of work package QA-01: (1) does the buffer handed to the face worker ever contain camera pixels outside the reveal region (hard gate, section 7.2); (2) how are task results that arrive late or belong to an old configuration handled; (3) exactly when does the reveal region close. Every test case is an automated test with numeric assertions; no case concludes by visual inspection. The "Run results" section (section 7) is generated by `npm run test:report` from the Vitest and Playwright JSON, together with the measurements each case records.

## 1. How to read

- A "test case" is one test (Vitest or Playwright); the case name is its title in the code. The "Section 7" column is the table in WORK-BREAKDOWN that the test file covers.
- "Measurement" is what a test records with `note()` (annotation `đo`) and `expectGateClean()` (annotation `gate cứng`) in `tests/e2e/helpers.ts`. The test still asserts these values itself with `expect`; the recorded values are only for cross-checking and to make the report reproducible.
- A "skipped" case is one that needs uncommitted local assets (`public/spike-assets/face.png`, `hands.jpg`): it runs on the development machine and skips itself in CI. The run in section 7 has both assets.
- Per-case time depends on the machine and the level of parallelism; CI runs 2 workers, so it is slower.
- The QA-02 bench (`tests/bench`, `npm run test:bench`) runs with its own Playwright configuration and is not part of this report; its measurements (multiple browsers, locked parameters) are in [benchmark.md](benchmark.md) sections 5 and 6.

## 2. Hard gate (section 7.2)

Merge-blocking condition: in every test case, the buffer sent to the face worker (and later the classifier worker) contains no camera pixels outside the mask's `cameraRect` at send time; with a quadrilateral mask (ROI-02, D-038) the cells inside the bounding box that are not open must be gray padding. Measured at the `onRestrictedFrame` probe (an `ImageData` copy of the letterboxed image right before `transferToImageBitmap`, section 5.9), not on screen. Two independent measurement methods:

1. **Marker colors** (`tests/e2e/restricted.spec.ts`): a synthetic scene with a magenta background (255, 0, 255) outside the window and a blue area (0, 0, 255) covering exactly `cameraRect`. Every valid pixel in the buffer has r = g (blue, gray padding and blends between those two colors); a pixel with r ≠ g is a trace of magenta. The count of r ≠ g pixels must be 0 for the smallest window at the top-left and bottom-right corners, a medium window, a large window (scale < 1), with mirror off, and for a skewed quadrilateral with holes (fake hands). Control at each position: shrinking the blue area by 1 px on each side must make the 1 px magenta border inside `cameraRect` appear in the buffer (bad > 0), proving that the measurement can see a 1 px deviation.
2. **Reference image** (`installGateAudit` in `tests/e2e/helpers.ts`, installed in every case that uses the synthetic source): for each buffer passing the probe, the test rebuilds in the page a reference image from the scene definition (`window.__scenario.scene()`: background, person area, static image) only within the buffer's `roiCam`, crops 1:1, paints the holes of the current mask gray, then letterboxes with the same formula as `src/core/letterbox.ts`, and compares it pixel by pixel with the buffer. A difference of more than 2 levels at any pixel is a failure (pixel outside the ROI, misaligned crop or unpainted hole). This method also covers scenes with a real face image and the fake-hand window; buffers captured while the scene is moving or the image has not loaded are skipped and counted separately.

The result of method 2 is on the "Hard gate measured with reference images" line in section 7; the count of pixels outside the ROI from method 1 is in the "Measurement" column of `restricted.spec.ts`.

Besides the two measurement methods, the following invariants are checked by script and lint on every run: `drawImage(` only in the compositor, `restrictedFrame.ts` and the synthetic source, always with a source rect (I2, I4); `restrictedFrame.ts` does not touch the DOM and crops from `source.drawable` (I1, I3); `src/face/` and `src/classify/` import only `src/core/` (I1); `createImageBitmap(` only in `handClient.ts` (`npm run check:invariants`, `npm run lint:boundaries`).

## 3. Late tasks (section 7.12 and table 7.1)

| Situation | Test case | Measurement method |
|---|---|---|
| Result arriving more than 250 ms late while the region is still open | `faceGate.spec.ts` "delayWorker(500) rồi đóng…" (local) | `delayWorker(500)`: `faceGate.rejected.stale` increases, the old face expires, state `searching` |
| Close while a task is running | same case as above | `delayWorker(500)` then `coverAll`: face empty immediately and after 900 ms, white canvas, 0 overlay pixels; on reopen the face returns with a new epoch |
| Grid or mirror change while a task is running | `face.spec.ts` "đổi lưới hoặc mirror khi tác vụ đang chạy…" | 3 s delay, an rAF poll in the page catches the moment a task has just been sent, then changes the configuration: until `FaceClient.stats.discarded` increases by 1, `faceGate.accepted` and the count of results rejected for epoch or `rejected-task` stay unchanged (read in the same pass); afterwards only new-epoch tasks are accepted (`faceGate.lastAccepted.epoch` equals the current epoch) |
| Window moved while a task is running | `faceGate.spec.ts` "kéo cửa sổ khi tác vụ đang chạy…" (local) | `faceMaxAge(4000)` widens the maximum age (debug scenario), 1 s delay so the task is still running when the window moves 3 cells: the first result the gate accepts after the move belongs to the old ROI (`lastAccepted.roiCam`, age > 250 ms) and the face stays in place (center offset ≤ 12 px from before the move), landmarks only inside the new stageRect; the next result from the new ROI also places the face at that same spot. The snapshot after the move is read in the page on rAF because the face of a result is kept for only 1 s (4 × maximum age) and a poll loop from Node may read late when the whole suite runs in parallel (fixed in UX-02 after one failure under load). Likewise, the "worker mặt sẵn sàng…" case of `face.spec.ts` waits for `faceGate.accepted > 0` instead of only waiting for the client to have a result, because the first few results may be rejected as too old when the worker starts slowly under load (fixed in CLS-01). The "nhãn gắn vào mặt" case of `classify.spec.ts` (CLS-02) also reads the face and the label in the same rAF snapshot in the page |
| Result with old epoch, rejected taskId, too old, mask gone | `faceValidate.test.ts` | unit: each rejection reason, exactly 250 ms is still accepted |
| `rejectAll` keeps busy until the result arrives, then discards it | `faceClient.test.ts` | unit with a fake worker |

## 4. Close timing (sections 7.7, 7.14, 7.16, 7.17)

| Event | Test case | Assertion |
|---|---|---|
| One hand missing (only one hand's points left) | `integration.spec.ts` "tay giả lập mở cửa sổ…"; `hands.spec.ts` one hand leaves the frame (local) | closes with `few-points` in the same frame; face empty; `accepting` off; no more buffers sent for 700 ms; the message names the missing slot |
| Crossed hands (uncertain frame) | `solver.spec.ts` "hai tay chéo nhau…" | closes with `ambiguous-hands`, four slots invalid, epoch unchanged; once uncrossed it reopens on the same cells with a new epoch |
| Four fingertips too close | `solver.spec.ts` "too-small…" | closes with `too-small` although four slots are valid; N min and point age apply immediately, epoch unchanged |
| Point too old | same case as above | a 300 ms stale point → `stale-point`; raising the age to 500 → open; resetting → closed |
| Tab hidden | `integration.spec.ts` "đổi nguồn cửa sổ…" | closes with `tab-hidden` inside the event itself (before rAF), epoch + 1, `accepting` off, white canvas; on becoming visible again it reopens (mouse and hands) |
| Camera stopped, watchdog sees no frames | `integration.spec.ts` "camera thật… dừng" | `no-camera`, white canvas, `accepting` off; on restart it reopens |
| Configuration change (grid, mirror, window source) | `roi.spec.ts`, `mask.spec.ts`, `integration.spec.ts` | `config-changed` then reopens with a new epoch; pixels inside the window match the new layout, outside the window white |
| User (Esc, leaving the hand source) | `roi.spec.ts`, `solver.spec.ts` | `user`, white canvas, no slots left |
| Reveal region state machine, camera and tab gates | `revealState.test.ts`, `closeGate.test.ts` | unit: epoch rules per close reason; `cameraGate`, `visibilityGate` |

## 5. Cases not yet automated

- Running all of section 7 with real hands and a webcam on the development machine (INT-01 step 4) and the 10-second right-hand label check (D-010): needs a webcam, not in the automated suite; recorded in WORK-BREAKDOWN section 7.16. The real-hand cases in the automated suite use the static image `hands.jpg` with the real worker.
- The y4m clip for the fake camera (TEST-00): needs ffmpeg; without it Chromium uses its default fake source (the camera cases still run and pass).
- Person and mannequin metrics (section 7.3, CLS-02): need a model trained on a real dataset; `tools/train/eval.py --doc docs/classifier-report.md`. The automated suite currently checks the pipeline with a stub model (`classify.spec.ts`, section 7.23). 15-minute soak: `npm run test:soak`, results in `docs/benchmark.md` (PERF-01).
- Lighthouse for the landing screen (UX-02, section 7.21): run manually with `npx lighthouse http://localhost:5173/#/ --only-categories=accessibility,best-practices` against the dev server; the 2026-09-18 run with Lighthouse 13.4.1, Chrome 153: accessibility 100, best-practices 96 (deduction for MediaPipe's INFO line via console.error). No added dependency, not in CI.
- Real dataset capture (CLS-01, section 7.22): needs participants who signed the consent form and a mannequin; the automated suite checks dataset mode with the synthetic source (samples are the exact `cameraRect` crop, never the raw frame) and the Python tools with a temporary dataset.
- A first-time user with a real webcam (UX-01, section 7.20): someone with no prior explanation opens the window following only the on-screen guidance; the automated suite checks each message with the fake camera and fake hands, which cannot replace this trial.

## 6. Reproducing

```bash
npm run test:report
```

The command above runs the unit tests with the JSON reporter (`reports/unit.json`), the e2e tests (`reports/e2e.json`, configured in `playwright.config.ts`), then rewrites section 7 with `tools/test-report.mjs`. To regenerate from existing JSON only: `npm run test:report:write`. CI (`.github/workflows/ci.yml`) runs the same check chain on Linux, regenerates section 7 and stores `reports/`, `test-results/` and this document as artifacts; the local cases are skipped there.
