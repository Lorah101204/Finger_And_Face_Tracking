# Performance benchmark and device matrix (PERF-01, QA-02)

Performance measurements of the PoC against the targets in WORK-BREAKDOWN section 3 ("Target rates": output ≥ 30 FPS, hand ≥ 20 Hz, face 10 to 15 Hz, classifier 3 to 5 Hz). Section 4 "Soak results" is generated by `npm run bench:report` from `reports/soak-samples.json` (15-minute soak, `npm run test:soak`, PERF-01). Section 5 "Device and browser matrix" (QA-02) is generated by the same command from `docs/benchmark-matrix.json`, which merges the results of `npm run test:bench` on each machine and browser. Section 6 records the locked parameters in `src/core/config.ts` and the reasons based on the measurements (D-045).

## 1. Measurement method

- **Sampler** (`src/debug/stats.ts`): every 250 ms it records the frame counter of the loop, face results, hand results and classification results; the rate is Δcount / Δt over a 2 s window. p50 and p95 inferMs come from the 20-sample window of `FaceClient`, `HandClient` and `ClassifierClient` (`src/core/latency.ts`); draw time and loop tick come from a 120-frame window. The "hiệu năng" (performance) overlay line on the stage and `window.__wct.stats.snapshot()` read the same sampler.
- **Rate control**: the face worker handles one task at a time, send interval `max(1000 / face.targetHz, p50 inferMs)` (targetHz 12), so the face rate never exceeds 12 Hz and drops by itself when inference is slow; the hand worker receives a new frame as soon as it is idle (no queue); the classifier uses `max(1000 / classifier.targetHz, p50)` (targetHz 4) on a second bitmap of the same crop.
- **Allocation and bitmaps**: each inference buffer is an `ImageBitmap` (`transferToImageBitmap`) whose ownership is transferred to the worker and which is closed in the worker after `detect` (even on error), or closed immediately in the client when it cannot be sent; the crop canvas and the letterbox canvas are reused (`restrictedFrame.ts`); the raw frame for the hand worker is a single `createImageBitmap` in `handClient.ts`, closed in the worker. The latency windows write in a ring over a fixed array. Otherwise each frame allocates only small objects (`FrameOutput`, the mask of the quadrilateral) and keeps no references; the soak measures the heap after GC to confirm there is no gradual growth.
- **React**: every status line reads through `useSyncExternalStore` at a 250 ms rate (`subscribeTick`, sampler), no per-frame `setState`; the draw loop lives outside React.
- **Soak** (`tests/soak/soak.spec.ts`, config `playwright.soak.config.ts`, `SOAK_MINUTES` default 15, `SOAK_SAMPLE_S` default 30): Playwright headless Chromium, synthetic source, hand-controlled reveal region (real hand worker with a local `hands.jpg`, or fake hands following a trajectory when the image is missing), face worker receiving buffers continuously, gate audit running throughout. Each sample: stats, JS heap after forced GC (`HeapProfiler.collectGarbage` then `Performance.getMetrics` via CDP; `performance.measureUserAgentSpecificMemory` needs COOP/COEP so it is not used), DOM node and listener counts, pending tasks, region state, page errors. Assertions in the test: no page errors, pending ≤ 1 in every sample, heap of the last third does not exceed the first third by more than 15 % or 8 MB, nodes and listeners do not grow gradually, fps of the last third ≥ 60 % of the first third, the face still produces results, the region is open more than 90 % of the time, the hard gate is clean.
- **Multi-browser bench** (QA-02, `tests/bench/bench.spec.ts`, config `playwright.bench.config.ts`, `npm run test:bench`): each project is a browser available on the machine: Playwright's Chromium headless shell (SwiftShader), installed Chrome and Edge (via `channel`, nothing downloaded; in the new headless mode they still use the real GPU through ANGLE), Playwright's Firefox and WebKit once `npx playwright install firefox webkit` has been run. Four test cases, `BENCH_SECONDS` seconds per measurement (default 20): (1) environment: browser, thread count, WebGL renderer, WebGPU adapter, the APIs the app relies on (`window.__wct.env`, the `env-stat` line of the debug panel), which delegate the face worker is ready with; (2) mouse window over `face.png` (local) or the synthetic background: stats every second and an rAF-driven collector in the page recording the timestamp of each result (p50/p95/max interval between two consecutive results) and the age at gate receipt for face and classification, the number of results dropped as too old; (3) classification forced to wasm (`ep=wasm`) to compare with the default EP; (4) real hands on `hands.jpg` (local) with `hands=CPU` then `hands=GPU`: Hz, p50/p95, result interval, reveal-region open ratio, thumb and index fingertip jitter on a still image (σ in camera px and cells). Raw results in `reports/bench-<project>.json`; `bench:report` merges them into `docs/benchmark-matrix.json` (one row per machine + GPU + browser + headless, a new measurement replaces the old one) and generates section 5.
- **Canvas 2D or WebGL** (PERF-01 step 6): keep Canvas 2D while the p95 draw time stays below the budget of one 60 fps frame (16.7 ms); measurements in the table below.

## 2. Limits of the headless measurements

Playwright's Chromium headless shell runs WebGL through SwiftShader (CPU) and has no WebGPU adapter, so MediaPipe's GPU delegate and ONNX Runtime's webgpu EP are not representative of the target machine: face worker (GPU delegate) p50 30 ms on a real GPU versus 110 ms headless when a face is present; hand worker with GPU delegate 2 Hz headless versus 29 Hz on a real GPU. Chrome and Edge run through Playwright's `channel` (including headless) use the machine's real GPU, so the matrix in section 5 has both the lower bound (shell) and the real measurements of that machine; the shell's `requestAnimationFrame` runs at 60 Hz, that of headless Chrome and Edge follows the display refresh rate (144 Hz on the development machine). CI (Linux, no GPU) has only the shell row.

### Reading the matrix

- **Chromium headless shell** is the lower bound (SwiftShader, no WebGPU): face 8.5 Hz with `face.png` (p50 110 ms), hands CPU 9.5 Hz, classification wasm; this is also the environment of e2e and CI.
- **Chrome and Edge 153 on RTX 3050**: output follows the display refresh rate, face 11.5 Hz due to rate control (p50 30 ms, age at receipt p95 68 ms), hands with GPU delegate 28.5 to 29.5 Hz (p50 25 to 27 ms) versus CPU 10.5 to 11 Hz, classification 4 Hz with both EPs: with the 360-byte stub model, wasm at 4.7 ms is faster than webgpu at 17 to 20 ms because GPU dispatch overhead dominates; S6 with MobileNetV2 gives the opposite result (webgpu 19 ms, wasm 59 ms), so the EP order stays per D-013 and is re-measured with `ep=wasm` once a real model exists.
- **Fingertip jitter on a still image** is the noise of the model itself (σ ≈ 0.05 px with CPU, 0.12 px with the GPU delegate, that is below 0.01 cells on a 64 × 36 grid): the 0.25-cell hysteresis has more than two orders of magnitude of margin; the jitter of a real human hand (tremor, breathing) is not measured yet because there is no webcam in the tooling environment.
- **Region open 100 %** in every hand measurement with a point age of 1000 ms (the bench sets it like e2e so the Hz measurement is not interrupted); the default point age is locked in section 6 from the measured result interval and inferMs.

## 7. Conclusion

On the target machine (desktop Chrome or Edge with a discrete GPU) every rate target of section 3 is met after switching the hand worker to the GPU delegate: output follows the display refresh rate, hands 29 Hz, face 11.5 Hz (capped by targetHz 12), classification 4 Hz, drawing under 1 ms per frame so Canvas 2D stays. Hand Landmarker on CPU (machines without a GPU, headless) is the only bottleneck (10 to 11 Hz) and is compensated by the 250 ms point age. Still pending: measurements on Firefox and Safari, classification Hz and EP with a real model, real human hand tremor with a webcam.
